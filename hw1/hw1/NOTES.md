## 4. C++ глазами питониста

| Python | C++ в этом ДЗ | Комментарий |
|---|---|---|
| `import x` | `#include <x>` | Буквально вставляет текст заголовка в файл |
| динамические типы | `int`, `double`, `std::vector<int>` | Тип известен при компиляции и пишется явно |
| `list` | `std::vector<T>` | Динамический массив одного типа; `v.begin()` / `v.end()` — «границы» |
| `for x in lst:` | `for (int& x : arr)` или `for (It i = a; i != b; ++i)` | `&` — ссылка: меняем элемент «на месте», а не копию |
| `lst.sort(key=...)` | `mySort(first, last, comp)` | Диапазон задаётся парой итераторов |
| `lambda a, b: ...` | `[](const Point& a, const Point& b) { return ...; }` | Лямбда; в `[]` перечисляют захваченные переменные |
| утиная типизация | `template <typename T>` | Шаблон: компилятор сам генерирует версию функции под каждый тип |
| `x = y` (ссылка на объект) | `x = y` копирует значение! | Чтобы не копировать, передают `const T&` |
| сборщик мусора | RAII | `std::vector` сам освобождает память в деструкторе при выходе из области видимости |
| исключение при выходе за границу | **неопределённое поведение** | Вот поэтому тесты гоняют под AddressSanitizer |

Ключевые понятия, которые встречаются в коде:

- **Итератор** — «обобщённый указатель» на элемент контейнера. Диапазон `[first, last)` — полуинтервал: `last` указывает на
  позицию *после* последнего элемента. Пустой диапазон: `first == last`. Размер: `last - first`.
- **Итератор произвольного доступа** — умеет `it + k`, `it - it`, `it < it`. У `vector` и у обычного указателя `int*` он такой.
  Поэтому `mySort(arr, arr + n)` работает и для обычного массива `int arr[]` (указатель — частный случай итератора).
- **Компаратор** — что-то вызываемое как `comp(a, b)`, возвращающее `true`, если `a` должен стоять *строго раньше* `b`.
  Это может быть функтор (`ByDistance`), лямбда или стандартный `std::less`/`std::greater`.
- **`std::move(x)`** — не «перемещает» сам по себе, а лишь разрешает забрать содержимое `x` вместо копирования.
  Для `int` и `Point` (две `double`) разницы нет, но код корректен и для «тяжёлых» типов вроде `std::string`.
- **`typename`** перед `std::iterator_traits<It>::value_type` — подсказка компилятору, что после `::` стоит *тип*.
- **`#pragma once`** — защита от повторного включения заголовка.
- **`inline`** у функций в заголовке — чтобы линковщик не жаловался на «множественное определение».

## 5. Алгоритм (merge sort) за две минуты

1. Диапазон короче или равен 16 → **сортировка вставками** (как раскладывать карты в руке).
2. Иначе делим пополам: `mid = first + n/2`, рекурсивно сортируем левую и правую половины.
3. **Слияние** двух отсортированных половин:
   - левую половину переносим во временный буфер;
   - два указателя: на начало левой (в буфере) и на начало правой (на месте); пишем результат с позиции `first`,
     каждый раз беря меньший из двух текущих элементов;
   - если одна из половин кончилась, остаток другой дописываем (остаток правой уже на месте).

Пример слияния. Левая `[1, 4, 7]` (скопирована в буфер), правая `[2, 3, 9]`:

| шаг | сравниваем | берём | результат |
|---|---|---|---|
| 1 | 1 vs 2 | 1 (левый) | `1` |
| 2 | 4 vs 2 | 2 (правый) | `1 2` |
| 3 | 4 vs 3 | 3 (правый) | `1 2 3` |
| 4 | 4 vs 9 | 4 (левый) | `1 2 3 4` |
| 5 | 7 vs 9 | 7 (левый) | `1 2 3 4 7` |
| — | левая кончилась | 9 уже на месте | `1 2 3 4 7 9` |

**Почему `O(n log n)`.** Каждое деление пополам уменьшает размер вдвое, поэтому уровней рекурсии `log₂ n`. На каждом
уровне все слияния вместе обходят ровно `n` элементов. Итого `n · log n`, причём **всегда**, а не «в среднем».

**Почему merge sort, а не quicksort.** Quicksort в среднем тоже `O(n log n)`, но при неудачном опорном элементе
(например, всегда первый, а вход уже отсортирован) вырождается в `O(n²)`; об этом прямо предупреждает задание.
У merge sort худшего случая нет, выбирать опорный элемент не надо, а ещё он **устойчивый** (равные элементы не меняются
местами). Цена — дополнительная память (`n/2` элементов).

**Две мелкие оптимизации** (обе объяснимы в одну фразу):
- порог 16 → сортировка вставками: на коротких кусках она быстрее рекурсии;
- в `mergeHalves` ранний выход, если `*mid` не меньше `*(mid-1)` — половины уже в порядке и сливать нечего.
  Именно из-за этого на отсортированном входе `mySort` работает *быстрее*, чем на случайном.

**Почему слияние не затирает ещё не прочитанное.** Левая половина сохранена в буфере, поэтому её затирать можно.
Правая читается с позиции `r`, а пишем в `out`. Записано всего `(взято слева) + (взято справа)` элементов, а слева
взять можно не больше `mid - first`, значит `out ≤ first + (mid - first) + (r - mid) = r`. То есть `out` никогда не обгоняет `r`.

## 6. Почему именно такие тесты

### Корректность (`tests/test_sort.cpp`, Debug + ASan)

В каждом случае проверяются **три** вещи: размер не изменился, `std::is_sorted`, результат — перестановка входа.
Одного `is_sorted` мало: функция, которая забьёт массив нулями, тоже «отсортирует». Перестановка проверяется так:
копии входа и выхода сортируются эталонным `std::sort` по *полному* порядку и сравниваются поэлементно.
Для `Point` полный порядок — по `(x, y)`: компаратор по расстоянию не различает разные точки на одной окружности,
а потеряться или подмениться не должна ни одна. (`std::sort` в тестах использовать можно: запрет касается только самой
реализации `mySort`.)

| Случай | Что ловит |
|---|---|
| пустой, один элемент | обращение к `*(first)` или `*(mid-1)` на пустом диапазоне, буфер нулевого размера |
| уже отсортирован | правильность раннего выхода из слияния |
| в обратном порядке | классический худший случай для quicksort; максимум работы у вставок |
| все равны | компаратор нигде не `true`; нет ли бесконечных циклов и потери элементов |
| случайные 10 / 1000 / 100000 | «обычная жизнь»: один уровень, несколько уровней, глубокая рекурсия |
| много повторов (5 значений на 10000) | ошибки при равенстве (`<` против `<=`) |
| **все размеры 0…100** | границы: порог 16/17, чётные/нечётные размеры при делении пополам, off-by-one |
| отрицательные числа, `INT_MIN`/`INT_MAX` | знак и переполнение (компаратор `a - b` здесь бы сломался) |
| `std::greater` | что параметр `Compare` реально используется |
| обычный `int arr[2000]` | что работают указатели вместо итераторов; ASan следит за стеком |
| известный ответ (`int`, `Point`) | независимая проверка «руками посчитанным» результатом |
| точки на одной окружности | компаратор считает их равными — не должны потеряться |
| отрицательные координаты, лямбда-компаратор | знак координат; что подходит не только функтор |
| устойчивость (бонус) | у merge sort она гарантирована, и тест это фиксирует |

Генератор случайных чисел — с **фиксированным зерном**: упавший тест падает так же при каждом запуске, его можно отлаживать.

**Тесты проверены «на прочность».** Я намеренно внёс в копию `mySort.hpp` шесть багов, и тесты упали на всех:

| Внесённый баг | Кто поймал |
|---|---|
| потерян остаток левой половины | перестановка и `is_sorted` (276 провалов) |
| слияние не вызывается | `is_sorted` (182 провала) |
| сдвиг в сортировке вставками на 1 короче | `is_sorted` (212 провалов) |
| сломана устойчивость | **только** тест устойчивости |
| буфер на 1 элемент меньше нужного | **только** ASan (выход за границу кучи) |
| середина `n/2 + 1` вместо `n/2` | ASan |

Отсюда два вывода для защиты: без ASan тест не заметил бы выход за границу массива, а без бонусного теста —
потерю устойчивости.

### Производительность (`bench/bench_sort.cpp`, Release, без санитайзеров)

- **Почему Release и без санитайзеров:** Debug не оптимизирует код (шаблоны и итераторы в Debug замедляются в разы),
  а ASan добавляет проверку на каждое обращение к памяти и искажает соотношение времён.
- **Размеры 10³…10⁶:** с шагом ×10 видно, как растёт время, и что отношение `mySort/std::sort` стабилизируется;
  10³ — почти «в кэше», 10⁶ — уже упирается в память.
- **Медиана нескольких прогонов:** устойчива к случайным выбросам (другой процесс, прерывание). Для малых `n`
  повторов больше, чтобы время не терялось в шуме таймера.
- **Копия данных перед каждым прогоном вне замера:** иначе сортировали бы уже отсортированное.
- **Проверка `is_sorted` после каждого прогона:** быстрая, но неправильная сортировка — не результат; заодно компилятор
  не может выкинуть вызов как неиспользуемый.
- **Формы входа при n = 10⁵** (случайный / отсортированный / обратный / все равны): по заданию нужно показать, что на
  отсортированном входе нет деградации. Порог в коде: хуже чем в 2 раза относительно случайных данных — печатается
  `DEGRADATION`.

## 8. Вероятные вопросы на защите

**Почему `O(n log n)`?** См. раздел 5: `log₂ n` уровней, на каждом уровне суммарно `n` элементов в слияниях.

**Какая сложность в худшем случае?** Тоже `O(n log n)` — от входных данных она не зависит. Память `O(n)` (буфер `n/2`).

**Почему не quicksort?** Выбор опорного элемента, худший случай `O(n²)`, нужен отдельный контроль глубины. Merge sort проще и
предсказуемее; цена — доп. память.

**Что значит «устойчивая» сортировка и где это в коде?** Равные элементы сохраняют исходный порядок. В `mergeHalves`
правый элемент берётся только при `comp(*r, *b)` — *строго* меньше; при равенстве берётся левый. То же правило в
сортировке вставками (`comp(key, *(j-1))` строгое).

**Зачем нужен буфер и почему его размер `n/2`?** Слияние на месте сложное; мы переносим в буфер левую половину
(`n/2` элементов), а результат пишем обратно в исходный массив. Буфер выделяется **один раз** в `mySort`, а не при каждом слиянии.

**Зачем `typename` и `std::iterator_traits`?** Нужен тип элемента по типу итератора (для временной переменной и буфера).
`typename` сообщает компилятору, что `::value_type` — тип.

**Почему `Compare& comp` во внутренних функциях, а в `mySort` — `Compare comp`?** Сигнатура публичной функции задана
заданием (по значению, как у `std::sort`). Внутри передаём по ссылке, чтобы не копировать компаратор на каждом рекурсивном вызове.

**Почему для `Point` надо передавать компаратор, а для `int` нет?** Значение по умолчанию — `std::less<Point>`, а он использует
`operator<`, которого у `Point` нет. Для `int` `operator<` есть. Аргумент по умолчанию «включается» только при использовании, поэтому
сам шаблон компилируется.

**Почему сравниваем квадраты расстояния?** `sqrt` монотонна на неотрицательных числах, порядок тот же; дорогой `sqrt` и его погрешность не нужны.

**Что будет, если компаратор написать как `<=`?** Нарушится требование «строгого слабого порядка» (для `std::sort` это неопределённое
поведение). У нас алгоритм не зациклится, но сломается устойчивость; правильный компаратор — всегда строгое `<`.

**Почему порог 16?** Эмпирически типичное значение: на коротких кусках у вставок меньше накладных расходов. Точная цифра — вопрос
подбора; можно менять `kInsertionCutoff` и смотреть бенчмарк (на корректность не влияет — тест «все размеры 0…100» покрывает границу).

**Почему тесты с ASan, а бенчмарки без?** ASan ловит выход за границы/use-after-free, но замедляет программу в разы и неравномерно;
для проверки корректности это ценно, для измерения времени — вредно.

**Почему `mySort` медленнее `std::sort`?** Раздел 7. А почему быстрее на отсортированных данных — ранний выход в слиянии.

**Что такое неопределённое поведение (UB) и при чём тут тесты?** Выход за границы массива в C++ не бросает исключение, а может «просто работать»
или тихо портить память. ASan превращает такие ошибки в немедленное падение с отчётом.

### Книга Кернигана и Ритчи

Важно: это книга про **C**, а задание — на **C++**. В ней нет `vector`, шаблонов, итераторов и лямбд, но есть полезная база:
синтаксис (циклы, функции, указатели, массивы) и три сюжета как раз про эту тему. Номера разделов даю по 2-му изданию
(*The C Programming Language*, ANSI C) по памяти — сверь с оглавлением своей книги:

- **глава 1** — быстрый обзор синтаксиса;
- **§3.5** — сортировка Шелла (ещё один способ сортировать, как «умная вставка»);
- **§4.10** — рекурсия, в примере — quicksort (`qsort`);
- **глава 5** (особенно §5.6 и **§5.11 «Указатели на функции»**) — сортировка строк с передачей функции сравнения.
  Это прямой предок идеи компаратора в `mySort`: «сортировка не знает, как сравнивать, ей передают функцию».

Указатель из K&R — частный случай итератора из C++. Это объясняет, почему `mySort(arr, arr + n)` работает на обычном массиве.

### Видео и интерактивные визуализации

Эти ссылки я открыл и проверил:

- [«15 Sorting Algorithms in 6 Minutes» (Тимо Бингманн)](https://www.youtube.com/watch?v=kPRA0W1kECg) — анимация и звук для 15 алгоритмов,

  можно ввести свой массив и прокрутить слияние вручную — идеально для подготовки к вопросам по алгоритму.
- [learncpp.com — Introduction to iterators](https://www.learncpp.com/cpp-tutorial/introduction-to-iterators/) — бесплатный текстовый
  курс по C++ (на английском); тот же сайт разбирает шаблоны, ссылки, `const`, лямбды. Пройди ему главы про шаблоны и итераторы.

Эти я **не проверял** (поиск не дал прямых ссылок), поэтому даю названия для поиска на YouTube, а не URL:

### Порядок подготовки (если мало времени)

1. Прочитать `mySort.hpp` сверху вниз с комментариями, параллельно прокрутив слияние на VisuAlgo.
2. Запустить тесты и бенчмарк на своей машине; посмотреть, как выглядит вывод.
3. Самому внести баг (например, поменять `comp(*r, *b)` на `comp(*b, *r)`) и посмотреть, что упадёт, — это лучший способ понять тесты.
4. Пройтись по разделу 8 и ответить на каждый вопрос вслух.
